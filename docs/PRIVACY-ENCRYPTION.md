# 個人データの保存時暗号化

この変更はアプリのソース実装です。既存のMac manual-demoや過去のバックアップは、PRのマージだけでは暗号化されません。既存データへの適用前に、停止した環境の複製で移行・復元を検証してください。DBの初期化、再シード、平文への自動ロールバックは行いません。

## 対象と境界

- `config/privacy.php` が列ごとの保護対象です。氏名・メール・住所・電話・児童情報・受給者証・支援記録・予約日付・シフト・給与・請求金額・監査ログ本文・連携ペイロード・キュー本文などを保護します。テーブルに存在する列のみ移行します。
- Eloquent と `DB::table()` の書き込み・読み込みの境界で暗号化/復号します。PDO、直接SQL、外部管理ツールの書き込みはこの境界を通りません。アプリで新たな個人列やSQLを追加するときは、保護設定と保存時検証を同時に更新してください。
- AES-256-GCMで各値をランダム化し、テーブル/列の文脈も認証します。暗号文の移し替え・破損・鍵不一致・移行漏れの平文は読み込みを拒否します。
- 検索用には独立した鍵によるHMAC列を使用し、メールのログイン・重複制約・完全一致を維持します。この列は画面/APIへ返しません。同値の有無と件数は隠しません。
- 部分一致・日付範囲・並べ替え・金額集計は復号した値で処理します。大きなテーブルでは全件候補の走査/並べ替えが必要になるため、実運用規模で計測してください。認可や事業所の絞り込みは従来のアプリの責務です。
- ID、外部キー、権限、処理状態、技術的な更新時刻、連携のリビジョン、公開マスターコードなどは構造情報として残します。パスワード/APIトークンの既存の一方向ハッシュも維持します。DBファイル全体を暗号化する機能ではありません。
- アプリのprivate localストレージ、ファイルセッション、永続キャッシュ、アプリログを暗号化します。PDF/CSV/ZIPの作成はメモリ内で行い、ストレージへは暗号文を保存します。添付は1件64MiB、ZIP元データ合計48MiBが上限です。
- 公開用ロゴ等のpublicストレージには個人資料を置かないでください。ダウンロードした利用者側のPDF/CSV、ブラウザー/OS/Docker/プロキシのログ、外部メールや決済先、ホストのスワップ・既存ディスクの未割当領域の保護は、このアプリ層の対象外です。ホストのディスク暗号化とアクセス権は別途必要です。

## 鍵

各アプリで独立した32バイトの `DATA_ENCRYPTION_KEY`、`DATA_LOOKUP_KEY`、`DATA_BACKUP_KEY` を使います。`APP_KEY` は変更しません。旧UCRM児童メモと既存セッションの復号にも必要です。CIに記載した鍵は公開されたテスト専用値で、実環境では使用禁止です。

`privacy:keys /非公開の保存先/data-keys.env` は新しい0600ファイルだけを作成し、鍵を画面に表示しません。DB/privateファイル/public配下へ保存することは拒否します。実行プロセスの環境にこのファイルを読み込み、DB・添付・バックアップとは分離して保管してください。鍵の別媒体の保護された回復用コピーを保持し、Gitやチャットには貼らないでください。鍵を紛失するとデータを復元できません。

`DATA_PREVIOUS_KEYS` は旧DATA鍵での読み込みを許可します。新規書き込みは現行鍵です。HMAC鍵を単独で変更してはいけません。完全な再暗号化・鍵ローテーションの自動運用はこのPRには含めません。

## 既存環境の移行順序（運用担当者向け）

以下は標準Laravel配置向けの処理順です。Mac manual-demoの `/demo/bootstrap.php` は設定を上書きするため、そのままホストの `artisan` やSQLiteへ実行しないでください。デモ用にはコンテナ内の設定・保存先・版を確認した更新手順が必要です。

1. アプリとワーカーの書き込みを停止。旧コード・DB・添付・セッション・ログ・既存バックアップの場所と件数を記録し、保護された複製を用意する。SQLiteのWAL/SHMと整合性を考慮し、稼働中DBファイルだけをコピーしない。
2. オフラインの複製に新コードと鍵を設定。設定キャッシュに旧設定が残らないようにする。DBと鍵を同じバックアップに入れない。MySQLのDDLはロールバックできないため、必ず複製で先に検証する。
3. `migrate --force` で対象列・検索用列・制約と既存行を移行。旧児童メモは旧APP_KEYで復号してから新方式へ移す。`privacy:migrate --verify` で平文の残り・認証・HMAC整合性を確認する。
4. `privacy:files`、`privacy:sessions`、`privacy:logs --migrate-legacy` で既存ファイルも移行。各 `--verify` を実行する。セッション移行では既存データと有効期限を維持する。
5. `privacy:cache` で旧キャッシュを検出。メンテナンス中に `privacy:cache --clear-legacy` で再生成可能な旧エントリーだけを除去する。新方式のキャッシュは保持する。共有Redis等は一括消去せず、別の範囲を限定した移行が完了するまで適用を止める。
6. 元のレコード数・ID・関係・連番・画面値を比較し、ログイン、検索、予約取消、連絡帳、シフト人数、請求金額、両アプリ連携と認可を確認する。
7. `privacy:backup /非公開の別保存先/snapshot.enc --offline` を実行し、空の復旧用DB/添付先へ `privacy:restore` して復元を検証する。既存DBや非空ディレクトリへの上書きは拒否する。バックアップ作成は全フレームの認証確認を行う。
8. 過去の平文SQLite/SQL/ZIP/CSV、更新用のbefore/afterスナップショット、ログイン情報のJSON、旧ログの別コピーなども、独立した暗号化保管先へ移して検証する。アプリ外の履歴ファイルは自動変換しない。旧平文のコピーが残ったまま「暗号化完了」と判定しない。
9. 複製での確認後に切替し、全ワーカーも同じ新コード・同じ鍵・同じprivate設定で起動する。失敗した場合は書き込みを止め、検証済み暗号化バックアップから別の空の復旧先へ戻す。更新の自動再試行やDB初期化はしない。

## バックアップ・調査

バックアップはlibsodium secretstreamで逐次認証して暗号化します。復元は全体の認証・終端確認を終えてから書き込みを開始し、SQLiteの整合性/外部キーを確認します。復元後もDB列と添付は暗号文のままです。復元にはBACKUP鍵に加え元のDATA/LOOKUP鍵とAPP_KEYが必要です。バックアップには鍵を含めません。ログは通常のtailでは読めず、認可された運用者が `privacy:logs --read=ログの絶対パス` でターミナルへ復号できます。復号出力を公開CIや共有ログに流さないでください。

保存時暗号化は、正規ログイン後の閲覧権限やアプリ/鍵を含むホスト全体の侵害を防ぐ仕組みではありません。運用開始の判定には移行先の実データ検証と鍵の復旧確認が必要です。
