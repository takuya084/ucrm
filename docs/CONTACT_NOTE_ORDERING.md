# 連絡帳の通知順序

ucrmは公開配信ジョブごとにcontact_notes.delivery_revisionを行ロック内で採番し、同じロック内で本文を読み直す。本文をキューに保持しない。通信前にコミットしてロックを解放する。失敗時に番号が欠けてもよい。次の試行は最新本文とさらに新しい番号を使う。同期済みの印は本文と採番後の元属性が変わらない場合だけ付ける。

p-yoyakuは同じ事業所・児童・日付・external_refの連絡帳に対しsource_revision以下の配信を200/applied:falseで無視する。同じ番号の異なる本文も上書きしない。新しい番号の受信後は番号なし配信を409で拒否する。初回の旧方式受信から新方式への移行は可能。

家庭側はp-yoyakuの保存時guardian_revisionとexternal_refを署名付き通知へ含める。ucrmは児童の親行と連絡帳をロックし、対応するucrm:IDが一致する既存連絡帳にだけ受信する。guardian_source_revision以下は無視し、新方式の受信後は旧方式を拒否する。明示的nullは新しい世代ならクリアとして反映する。既読は単調な状態なので採番せず、external_refで対象を確認する。番号なしの旧家庭通知は移行前の既存互換としてのみ受け付ける。

## 反映

両アプリのコード・追加migrationをセットで準備し、連携書込みとワーカーを止めて実行中処理の完了を確認する。バックアップ後、両方のmigrationとコードを反映して新ワーカーを再起動する。片側だけの更新や新旧ワーカーの混在は避ける。GitHub上のPRマージだけでは実環境へ反映されない。

p-yoyakuで変更前にシリアライズされた通知ジョブはexternal_refを含む宛先スナップショットを持たず、安全のため送信拒否になる。未処理・失敗ジョブを確認し、宛先と最新記録を検査して新コードで再投入する。生のキューや本文・秘密鍵をログやチャットへ貼らない。番号や記録を勝手にリセットしない。DBバックアップの片側だけの復元は番号を巻き戻す可能性があるため別途復旧計画が必要。

## 検証と残る範囲

単体/回帰テストで採番と本文の組合せ、逆順/重複/旧方式/不正番号/別IDの拒否を確認する。非公開p-yoyaku側の実HTTPテストで、実ジョブを2プロセス動かしてloopbackプロキシに古い通知を保留し、新しい通知を先に受信させる。両方向で番号と最新本文が残ることを確認する。固定時計でも検証でき、sent_atを順序判定に使わない。

常駐ワーカーの停止・更新・再起動、両アプリをMySQLで同時稼働するHTTP並行テスト、SoftDeleteに伴う取り下げ連携、タイムアウトによる同じ副作用の重複は別工程。公開取り下げの追加実装はCONTACT_NOTE_WITHDRAWAL.md（p-yoyaku側はWITHDRAWAL.md）を参照する。SoftDelete連携は引き続き別工程。Mac・実DB・本番は今回変更しない。
