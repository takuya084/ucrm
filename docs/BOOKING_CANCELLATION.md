# 予約取消・順序逆転防止

## 変更する動作

- ucrmの欠席・キャンセル・ソフト削除は、予約作成ではなく `PUT /api/integration/bookings` の `cancelled: true` で通知する。時刻が両方空の通常予約とは区別する。
- p-yoyakuは対象予約を削除し、対象が既に存在しない場合も処理済み番号を残す。番号の小さい登録・取消は反映しない。同番号・同内容は重複として成功、同番号・異なる内容は409。
- 事業所・外部参照・児童・日付の対応を固定する。他事業所・先生・別児童・別日への参照付け替えは拒否する。
- p-yoyakuで手動取消した場合も、取消確認番号を即座に保存する。通信途中にあるucrmの古い更新は、通知番号が大きくても確認番号が一致しない限り再予約できない。
- ucrmは取消確認番号をAPI応答・署名済み通知から受け取り、再予約時に送る。p-yoyakuの取消を受信した後、ucrmでメモだけ保存しても予約を復活させない。新しい送迎指定を伴う明示的な再予約は可能。
- ucrmで欠席・キャンセル・削除した出欠記録は、遅れて届いた予約通知では復活させない。出欠の復帰はucrmで明示操作してから行う。p-yoyakuの取消で出欠statusや請求対象を勝手に変更せず、送迎フラグ・時刻だけを解除する。
- 待機中のジョブは実行時に最新DB状態を読む。古い作成ジョブが取消後に動いても取消を送り、古い削除ジョブが明示的な再予約後に動いても現在の予約を送る。
- 通知はDBコミット後にキュー投入する。HTTPはDBロック解放後に行い、番号の確定はHTTPより先に永続化する。
- p-yoyakuからの通知も施設・児童・日付ごとの番号で照合する。取消通知が先行しても削除記録を残し、後から届く古い登録通知を無視する。日付変更は旧日の削除と新日の通知を分ける。

## 認証・失敗

新APIも既存のSanctum＋同一事業所の先生adminに限定する。WebhookのHMAC・時刻検査と確定済み請求月の保護を維持する。
予約同期では施設専用トークンが必要で、共通トークンへfallbackしない。失敗・非2xx・不正な応答はジョブ失敗として扱い、既存のキュー再試行上限を超えればfailed jobとして残る。旧作成APIへの代替送信はしない。運用画面での未送信一覧・手動再送UIは本変更に含めない。

## 導入順序（実環境操作はこのPRで行わない）

1. 両アプリの連携書込みとキューワーカーを止め、実行中ジョブの終了を確認する。未処理キュー・既存データは削除しない。
2. 両リポジトリの対応PRを取り込み、両方の追加migrationを適用する。既存DBの再作成は不要。
3. 新しいコードで両ワーカーを再起動し、両アプリの連携書込みを再開する。片側の旧コードと混在運用しない。
4. テスト用事業所で「登録→取消→取消の重複→明示的な再予約」を確認する。409が継続する場合は紐付け・取消通知の配送状況を確認し、DB番号や取消記録を削除して回避しない。

旧キューに保存されたジョブも新コードで最新状態を読み直す。既に送信済みで番号のない旧通知は、番号付き状態または取消記録が存在する対象には409で拒否する。番号未導入の既存対象は初回移行まで従来形式の受信を許可するため、移行時の停止・排出が必要。
既存予約の自動一括取消、古い不整合の自動修復、ロールバック時の番号初期化は行わない。外部参照の児童・日付を変更する移設は自動対応せず409とする。

## 検証範囲

- 架空データ、HTTP fake、SQLiteメモリDBで実Controller・Observer・Jobの登録/取消/重複/逆順/復帰・認証・未連携・配送失敗を検証。
- 共通 `tests/fixtures/integration/booking-sync.json` をucrmの実送信JSONとp-yoyakuの実受信ルートに適用。
- 共通 `booking.json` をp-yoyakuの実Observer→署名付きHTTPとucrmの実Webhookに適用。
- MySQLの独立2プロセスで、同じ事業所への登録revision 1と取消revision 2が並行しても、最終状態が取消であることを確認する。
- 既存PHP・ブラウザ回帰テストを維持。実Mac・実DB・Stripe・メール・Gatewayは操作しない。

これは二つの実アプリを同時起動して実HTTP接続するE2Eではない。通信切断・長時間障害後の運用、別DBにまたがる完全な分散トランザクション、連絡帳、請求確定との並行競合を全て保証したものではない。連携全体のリリース判定は別途継続する。
