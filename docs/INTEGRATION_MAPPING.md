# 連携先の曖昧な紐付けを拒否する

## Webhook受信

- `yoyaku_business_id` に一致する施設が複数ある場合は409で拒否する。
- 署名検証済み施設内で `yoyaku_user_id` に一致する有効な児童が複数いる場合も409で拒否する。
- 予約作成・変更・取消と、連絡帳の既読・家庭側記入に共通の判定を適用する。拒否時は出欠・連絡帳・予約番号状態を更新しない。
- 児童検索は施設内に限定する。別施設に同じ番号の児童がいる場合は重複とは扱わない。削除済み児童は従来通り受信対象外。
- 施設・児童が見つからない場合、署名不一致、期限切れ通知、請求ロック、取消状態の扱いは従来のまま。

## API送信

`YoyakuApiService` の各操作は、明示された施設の `yoyaku_api_token` だけを使用する。施設IDが未指定・不正・存在しない場合や、専用トークンが未設定・空白のみの場合はHTTPを送らない。共通設定 `services.houkago_plus.api_token` への代替は行わない。

通常の参照・更新メソッドは従来の失敗値（nullまたはfalse）、番号付き予約同期は例外を返す。同期の失敗を旧APIへの再送で回避しない。

## 導入・確認

追加migrationはない。共通トークンだけで運用していた施設は、施設専用トークンを設定してから利用する。重複紐付けのある施設はWebhookが409になるため、正しい対応を人が確認して修正する。既存データの自動削除・統合は行わない。

この変更の範囲はWebhook受信時の重複拒否とAPIクライアントのトークン選択。CSV・アカウント作成時の重複予防、実績取込の突合処理、送信ジョブの紐付け検証は別途確認が必要。データベースの一意制約や紐付け設定の同時変更まで保証する変更ではない。

## 検証

`tests/Feature/IntegrationMappingTest.php` で不足・不正な施設認証、施設ごとの認証分離、施設・児童の重複拒否、既存出欠・連絡帳・予約状態の保持、正常な施設分離、削除済み児童の扱いを検証する。

PRの隔離CIは架空データ・SQLiteを使用し、PHPテスト実行時のネットワークインターフェースを分離する。実環境・実DB・Macへの反映は別工程。
