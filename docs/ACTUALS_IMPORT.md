# 送迎実績の取り込み

`php artisan yoyaku:import-actuals --date=2026-11-04 --facility=1`

施設専用トークンでp-yoyakuの `/api/schedule/actuals` を取得し、施設・児童・日付が一致する既存の出席記録（UsageRecord）の `pickup_done` / `dropoff_done` だけを更新する。実績時刻がnullなら未実施、日時があれば実施とする。登所・降所時刻、メモ、出欠状態、予約番号や取消トークンは変更しない。取込中は予約送信だけを抑制し、監査ログは残す。

旧処理はDailyServiceRecordに存在しないfacility_id/child_id/service_dateでupsertしていた。DailyServiceRecordは請求計算で生成されるため、直接作成・更新せず、計算元の出欠記録へ取り込む。既存の下書き請求には自動反映されない。必要な確認後、通常の請求再計算を行う。サービスコードや加算単位はこの処理で作成・変更しない。

## 更新しない対象

- 未紐付け児童、出欠未作成、削除済み児童・出欠、欠席・取消の出欠はスキップする。出欠の新規作成・復活は行わない。
- 受信済みの予約状態が取消なら、古い実績が返ってきてもスキップする。
- 空の実績一覧は、既存フラグを消さない。
- 同じ児童番号が別施設にある場合は、指定施設の児童だけが対象になる。

## 失敗として停止する条件

施設番号の重複、対象児童番号の施設内重複、同じ児童の実績行重複、日付不一致、必要項目不足、不正な日時、取得失敗・施設専用トークン不足は失敗にする。紐付けやレスポンスの不備では、その施設の日次バッチを途中まで取り込まない。HTTP中に施設番号・トークンが変わった場合も停止する。

対象月の請求がconfirmed/submitted/completed/calculatingなら更新しない。エラーはコマンドの終了コードを非ゼロにし、正常な0件取込として扱わない。全施設実行では、先行施設の完了分は保持し、失敗した施設以降を停止する。

HTTP中はDBロックを保持しない。更新時には既存の施設・請求期間・児童・出欠をトランザクション内で読み直す。ただし設定の全更新経路との排他や、一意制約のない紐付けの同時追加まで保証するものではない。設定変更・請求計算と同時に取込を実行しない運用とする。実HTTP E2E・本番導入は別工程。

追加migrationなし。PR #5の施設専用トークン必須化を前提とする。`tests/Feature/YoyakuActualsImportTest.php` に架空データでの検証を追加。
