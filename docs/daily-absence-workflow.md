# 欠席連絡・相談記録（2026-11-21）

## 根拠・判断

- 山形市 令和6年度集団指導 1回の相談援助を複数日に算定しない取扱い
  https://www.city.yamagata-yamagata.lg.jp/_res/projects/default_project/_page_/001/015/939/r6syuudannsidou.pdf

原則は前々日・前日・当日の連絡、児童の状況確認・相談援助・記録、通常月4回まで。
営業日で前2日を探索し、連絡日が休業日でも範囲内なら日付条件は満たす。370日探索して不明なら要確認。
特例（月8回等）は適用事業所・対象児童・稼働率等の確認が必要なため自動承認しない。
「算定候補」は日付と記録の補助判定であり、請求送信・入金・国保連の受理を意味しない。
当該自治体の運用、受給者証・請求実績票等も請求時に確認する。

## 記録

連絡日時（JST）、理由、手段（電話/LINE/アプリ/対面/メール/その他）、連絡者、受付職員、
相談援助を行った職員の氏名と職名、児童の状況、相談援助の具体的内容・経過、次回利用予定日。
予定あり・急病等・受入体制あり・相談援助実施を未確認/はい/いいえで記録する。
未完成でも保存でき、未入力を明示する。実施していない相談内容や日時の自動補完はしない。
通常の算定確認は管理者・児発管のみ。記録不足・対象外・月4回超・特例には確認を付けられない。
同じ児童・同じ相談日時を複数日に使った場合は対象外。別時刻で転記した同一相談は自動検知できないため確認が必要。
欠席取消も履歴に残す。予約を削除せず送迎対象から外し、取消後は予約を利用できる。

## 連携と責任範囲

p-yoyaku単体ではp側DBに保存。UCRM単体ではU側DBに保存。
連携時はp側が正本。UCRMからの参照・更新は施設別APIトークンを用いたプロキシ。
両方で編集でき、tenant/child/dateごとのrevision一致が必要。競合は422、全書込み前に確認。
事業所行ロックで同月の確認回数も直列化。変更履歴はabsence_notice_versionsに追記。
UCRMは出欠表示へ欠席を投影するが、GETで出欠DB・請求データを書き換えない。
請求前にメニュー「出欠・利用実績」で対象月の出欠を確認・保存する。
UCRM請求計算は連絡あり欠席だけでは加算を算定せず、正本記録の通常算定確認と現時点の条件が必要。
連携取得失敗時は確認不能を表示し、加算は対象にしない。
営業日設定は欠席判定用。予約受付の休業日とは別設定なので、履歴期間に合わせて確認する。
更新時は両アプリの2本のmigrationが必要。外部APIを使う機能は両方の更新完了後に有効となる。

## 送迎

従来の担当IDは保持し、各方向に任意の担当2を追加。担当2は担当1と異なる同事業所の有効候補のみ。
親送迎・時刻なしの方向は担当を解除。revisionと予約snapshotは2人分の変更も検出。
一覧は時刻→学校名→児童ID。場所schoolは同事業所の学校名で表示、名称未登録も明示。
Excel貼付の既存6列は順序を保持し、担当2の2列を末尾に追加する。
